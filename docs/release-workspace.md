# AIリリース候補の使い方と実装

今回の対象は、AIへの相談から変更内容の確認、動作テスト環境への反映と復元まで。Toolkit全体の調査機能を作り直す変更ではない。

公開候補は **v2.3.0（未公開）**。公開済みの最新版 **v2.2.6** と区別する。現在の本体の基準版は `9ecd322`。検証専用アプリで選択肢・計算式・JavaScriptの変更とフィールド削除を確認した。過去の機能の確認は実施時の版を併記し、最新版ですべてを再実施した意味にはしない。候補の変更点は[リリースノート](RELEASE-NOTES-2.3.0.md)を参照。以下は2026-10-25時点の記録に基づく。

## 使い方

1. 「開発支援」を開き、上部の［接続］でAIサービスへの接続を確認する。
2. 相談欄に、変更したい動きと維持したいことを入力して［送信］する。最初の送信では、アプリ設定と登録済みJavaScriptの本文などをAIサービスへ送ることへの同意を確認する。レコードの値・添付ファイル・接続の認証情報は送らない。
3. 相談と仮案を同じ画面で見ながら、質問や修正を送る。画面が狭い場合は縦に並ぶ。内容が決まったら［この案で作成］を押す。この操作ではkintoneを書き換えない。
4. 「今回反映する内容」と、制約・反映前に必要な確認事項を読む。根拠は返答ごとの［この返答の根拠］、コードと検証結果は［JavaScriptを見る］［確かめたこと］で開ける。すべての詳細を順に読むことを前提にしない。
5. 内容を確認して［動作テスト環境に反映］を押す。設定とJavaScriptの反映結果を読み、実際の画面で動作を確かめる。AI機能から運用環境へ反映することはない。

未送信の文章がある間は、作成・反映などの操作はできない。入力した修正を送るか、不要な下書きを消してから進める。

作成が途中で止まったときは、完成した内容と残っている内容、理由を表示する。［残りを作成］は利用者が続きを依頼する操作であり、自動では繰り返さない。反映の結果が不明な場合は、同じ内容を再反映せず、現在の設定を確認する。

反映結果に［この反映の変更を戻す］が表示される場合は、対象を確認し、［反映前の状態に戻す］で実行する。確認だけで閉じるときは［戻さずに閉じる］を押す。後から別の変更が加わっている場合など、戻せないこともある。

## 新しいフィールドの配置

AIは現在のフォームを見て、新しいフィールドを追加する位置も案に含める。既存フィールドと同じ行の左右、既存フィールドのある行の上下、既存グループ内、フォームの末尾へ配置できる。追加したフィールドを基準に次のフィールドを並べることもできる。

反映前の「今回反映する内容」で、フィールドの用途と配置を確認する。配置を変えたいときは、採用・反映する前に相談欄で修正する。Toolkitはフィールドコードと行・グループの構造で指定を実行し、文章から場所を推定しない。

今回の対応は新規フィールドの配置であり、既存フィールドの移動、幅・高さの調整、新しいグループやテーブルの作成、テーブルへの列追加は含まない。既存の配置・ラベル・スペース等を保ち、配置先がなくなった場合や承認後に設定が変わった場合は反映を止める。

この機能には配置に対応したAIサービスが必要。未対応の接続先では有料の相談・計画を送る前に止まるため、更新時はGatewayを先に更新する。固定応答テストに加え、配置を尋ねる実AIの会話と、「請求書番号」を「備考」のすぐ上の独立した行へ追加する実反映を確認済み。既存10行の並びと表示幅、空欄での保存も確認した（Toolkit 78679a5、アプリ353の動作テスト環境）。すべての配置方法を実画面で試したわけではない。

## 選択肢・計算式・フィールド削除

選択肢の変更・削除、フィールド削除、計算式の変更を相談できる。AIは取得した設定と登録済みJavaScriptを確認し、影響する変更を依存関係に沿って計画する。JavaScriptから参照を外してからフィールドを削除する計画では、登録と読み戻しが完了してから削除へ進む。登録に失敗した場合は依存する削除を止める。

選択肢の変更はドロップダウン・ラジオボタン・チェックボックス・複数選択に対応する。フィールド削除は通常のフィールドが対象で、テーブルやグループ全体、テーブル内の列、システムフィールド、ルックアップの削除は含まない。

選択肢やフィールドの削除には既存データへの影響がある。入力済みの値を戻せる保証がないため、これらを含む反映には一括の自動復元を提供しない。必要なデータを事前に保管し、反映前の確認事項を読む。レコードの一括変換・旧選択肢を使うレコードの調査や移行を自動で完了する機能ではない。運用環境へ反映する前に実際のデータへの影響を確認する。

検証用の変更前設定とJavaScriptを用意したアプリ398の動作テスト環境で、8択から6択への変更、計算式・説明の更新、紹介経路2項目の削除、作成・編集・保存を確認済み（Toolkit 9ecd322）。外部クライアントの実コードや業務データを使った試験ではない。この変更には一括の自動復元は提供しない。モバイルは今回の計画に含まれず、未実施。

## 無料の資料作成

上部の［資料を作成］から、外部AIへの相談用・変更計画用の資料と、アプリ仕様書・要件定義書・引継ぎ資料などの下書きを作成できる。Nest Rec AIの契約は不要。

資料の種類・対象・形式を選び、［資料を作る］を押してから、［コピー］または［ファイルで保存］を使う。この操作自体はAIサービスへ送信しない。レコードの値・添付ファイルは含めず、資料に含めた情報や取得できなかった情報を画面で確認できる。外部へ渡す前に内容を確認する。

採用した案から計画を作成済みの場合、資料には修正後に採用した内容・前提・制約をそのまま含める。最初の依頼、修正コメント、確認事項への回答は履歴として分け、後の修正より前の条件を現在の合意として扱わない。Markdown・JSON・外部AIへの指示文で同じ情報を使い、コピーとファイル保存でも保持する。資料作成のためのAI呼び出しや文章の再解釈は行わない。

## 再読み込みと更新時の注意

会話、承認した内容、反映結果、元に戻すための記録はページ内だけにある。再読み込みやページを閉じる操作で失われ、旧版を入れ直しても復元できない。離脱時の注意表示は、自動保存や自動復元を意味しない。

生成コードは［コードをコピー］［ファイルで保存］で残せる。ただし、これらや無料の資料作成は、会話・復元用データの保存と読み込みの機能ではない。更新前には必要な記録を残し、処理が完了していることを確認する。

ユーザースクリプトの更新は、同じブラウザープロファイル内の一致するアプリに及ぶ。開いたままのタブは、再読み込みするまで旧版が動く。接続設定はkintoneのホスト単位で共有し、アプリごとの設定ではない。

## 確認済みの範囲

- **実際のAIによる会話**：備考のPC編集制御をモバイルにも広げる修正、経理確認を追加してステータス別に編集可否を変える修正を確認済み。修正コメントだけで作成を始めず、採用した変更が最終案と生成コードへ引き継がれた。
- **反映と実際の動作**：検証専用アプリ397で設定3件・既存JavaScript2本を反映し、100万円以上と未満の承認経路、差し戻し、作成中・経理確認・承認済みの編集制御を確認済み。PCと、PCのEdgeで開いたkintoneのモバイルWeb画面で確認した。元の業務アプリ353の運用環境を更新したものではない。
- **会話欄の配置を確認した版**：efeccd6を同じ検証タブへ入れ、stagingへの接続、相談と変更案の同時表示、文字110%、下書きの保持、補助画面の開閉を確認済み。更新後に有料AIの新しい会話は送っていない。
- **無料の確認**：固定応答での作成・反映・復元、失敗時の扱い、無料資料、画面幅などを試験している。固定応答による合格と、実際のサービスを使った確認は区別する。

追加・配置と選択肢・削除の確認は上記の各節に分けた。経理確認の会話と反映はbbb6fbbで実施した。efeccd6との差は表示と関連テストだけで、採用・生成・反映の処理は変えていないため、その確認結果を引き継ぐ。その後、リリース候補では一部だけ元に戻せた場合に残りを戻す処理を修正している。この修正を含む候補全体を、実際のkintone画面で再確認済みとはしない。

実スマートフォン端末、iOS/Androidのブラウザー、kintoneのモバイルアプリ、タッチ操作は未確認。今回の新画面での実際の設定の復元、すべての業務要件・ブラウザーでの動作を確認したわけではない。会話中の注意・制約と反映後の確認は引き続き必要である。

## 開発者向け：構成と検証責任

候補の正確なコミットと試験結果は、開発時の専用AI作業場所にある `AI/docs/contracts/codex-release-redesign-20261024/RELEASE-READINESS-20261025.md` に集約する。同じフォルダーの `COMPLEX-SCENARIO-VERIFY-20261024.md`、`COMPLEX-APPLY-VERIFY-20261024.md`、`CHAT-LAYOUT-REAL-VERIFY-20261024.md` が実際の確認記録。これらは公開Toolkit単体には含まれない作業用資料である。

次の5ファイルがAI画面のソースである。

| ファイル | 責任 |
| --- | --- |
| src/release-workspace.js | 明示的な採用、状態遷移、成果物と承認の照合、実行記録 |
| src/release-context.js | 取得した事実、利用者の依頼と回答、採用内容の引き継ぎ |
| src/release-execution.js | 設定・JavaScriptの実行部品の接続、部分失敗と復元 |
| src/release-view.js | 相談・変更内容・結果の表示 |
| src/release-runtime.js | 既存の接続、利用制限、取得、無料資料機能との接続 |

`node tools/build-release-workspace.cjs` で本体の生成区間へ埋め込む。生成区間を直接編集しない。`--check` は編集元と埋め込みの一致だけを確認する。認証、設定取得、設定・JavaScriptの書き込み部品などの既存コードは本体に残る。

Toolkitは自然文から効果・担当・API可否を再推定しない。コードの検査と模擬テストはAIサービス側が行い、Toolkitは受け取った結果と、対象・検証した本文・登録先が一致することを照合する。書き込み前の最新設定、権限、承認後の変化、読み戻し、復元対象の確認は実行部品が担当する。AIの説明だけを合格や安全性の保証にはしない。

原価やトークンの内訳は通常表示に出さない。内部の利用制限と終了不明の記録は保持する。仮案の採用と、kintoneへの反映承認は別操作である。

旧 `KTAiConversation`、`KTAiChatUi`、`KTPlanReview`、`KTCodeReview` を新画面の利用先として案内しない。現行の内部構成はREADMEの表と上記の5ファイルを参照する。

## 開発者向け：無料の確認

```powershell
node tools/build-release-workspace.cjs --check
node tools/test-release-workspace.cjs
```

全ファイルの終了コードで集計し、結果を無視対象の `tests/.build/release-check/` に保存する。`--unit` を付けるとファイル名が `-browser.test.js` で終わる試験を除く。

ブラウザー試験はPlaywrightとEdgeを使用する。専用の一時プロファイルで外向きの要求を遮断し、AIの応答とkintoneを固定応答に置き換える。実サービスへの接続はしない。Playwrightのパスは試験ファイルの環境変数で指定できる。

AIリポジトリの `sandbox` では `npm run test:release` が、新しい入力と本物のGateway、ローカルの模擬テスト環境をつなぐ。AI応答だけを固定する。`KT_TOOLKIT_DIR` でこのToolkitの作業ディレクトリを指定する（省略時はAIと同じ親のToolkit）。

旧テストの整理は `tests/release-test-migration.json` に記録した。旧画面・旧意味判定を試すものは置き換え、非AI機能と実行時の安全性は維持する。件数の減少を検証の強化とは扱わない。

## 一般公開前に区別すること

現在確認できているのはCodex専用候補とstagingの組み合わせであり、公開GitHubの配布物や運用用AIサービスを今回更新したものではない。

一般公開前には、候補番号2.3.0・対象コミット・配布本文を照合し、公開先で使うAIサービスと模擬テスト環境の対応を確認する。新画面には `releaseWorkspace`、`artifactOutcome` などの対応が必要で、stagingの合格を運用用サービスの確認として扱わない。必要なサーバー側更新を済ませてからユーザースクリプトを配布する。

既存の公開経路はREADMEにあるGitHubのUserScriptであり、プラグインZIPではない。公開先への反映・タグ・配布の実行は、この候補の作成やローカルの再インストールとは別である。

## 関連する任意の提案

AIが返したorigin=suggestionの項目は「あわせて検討できること」に分けて表示する。通常の「この案で作成」では採用したbehaviorsから除外し、その採用内容を計画・保存資料へ渡す。元の仮案は維持し、利用者が追加を求めた後にAIがorigin=userとして更新した案は通常どおり採用する。文章の意味をToolkitで再判定しない。任意案のための別のAI呼び出しや選択状態は持たない。


## プロセス管理の経路確認

既存の反映部品が、取得した設定と今回の手順を合成し、最初のステータスからアクションの向きをたどって新しいステータスに到達できるか確認する。自己遷移や孤立した循環だけでは到達可能としない。反映前の準備と書き込み直前で同じ合成処理を使い、二重の判定状態は持たない。

既存の到達不能なステータスは過去のレコードを持つ可能性があるため一律に削除・停止しない。終点の出口を必須にしない。条件式の充足可能性、利用者・作業者ごとの実行可否、既存経路の意図的な廃止はこの到達性判定の対象外で、接続の確認を動作の保証と呼ばない。文章解析や有料の再試行は追加しない。
